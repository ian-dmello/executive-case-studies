# Executive Case Studies

## Overview

This repository presents a curated portfolio of executive-level case studies covering strategy, transformation, governance, internal audit, risk, finance, operations, investment, forensics and technology.

The portfolio is organised **by professional practice** so that readers can quickly navigate to the type of work most relevant to them.

The case studies are based on professional, academic and project experience and are presented for portfolio purposes. Where a case is relevant to more than one practice, it is maintained in **one primary location** and cross-referenced from the relevant secondary practice.

# Recommended Case Study Structure

Where practical, each case study should follow a consistent structure:

1. **Executive Summary**
2. **Business Context**
3. **Problem / Objective**
4. **Scope**
5. **My Role**
6. **Approach / Methodology**
7. **Key Analysis**
8. **Key Findings**
9. **Recommendations**
10. **Outcome / Impact**
11. **Skills & Capabilities Demonstrated**
12. **Key Learning**

Not every case needs every section. The objective is consistency without forcing an artificial structure onto a case that does not support it.

# Portfolio Presentation Principles

### 1. One master copy per case

A case study should exist in only one primary folder.

If it is relevant to multiple practices, use cross-references rather than duplicating the complete case.

### 2. Practice first, case second

Readers should be able to identify the professional capability before opening an individual case.

### 3. Avoid overclaiming

Clearly distinguish:

- Professional engagements
- Academic projects
- Personal learning projects
- Team projects
- Independent work

### 4. Separate technology projects

AI, ML, cybersecurity and other technology-learning projects are grouped under **IT Projects** rather than being presented as conventional consulting engagements.

### 5. Use consistent naming

Use short, descriptive, lowercase folder names with hyphens.

Example:

`enterprise-risk-management-framework`

rather than:

`Enterprise Risk Management Framework Final Version 2`

### 6. Keep the repository executive-friendly

The repository should demonstrate breadth without becoming a document archive.

The strongest cases should receive the greatest depth; supporting cases can remain concise.

### 7. Cross-reference rather than duplicate

Secondary practice areas should point readers to the master case.

This prevents version-control problems and keeps future updates manageable.

### 8. Protect confidentiality

Client names, confidential information, personal data and commercially sensitive information should only be included where appropriate and already publicly available or suitably anonymised.
